## 🔑 核心概念（必须掌握）

### 1. 为什么用几何均值（Geometric Mean）？

当你用 N 个 benchmark 测试两个处理器 A 和 B，需要给出一个汇总的"平均加速比"时：

| 汇总方法 | 公式 | 问题 |
|---------|------|------|
| 算术均值 | (S₁+S₂+...+Sₙ)/N | 受极端值影响大；加速比 A/B 和 B/A 不对称 |
| **几何均值** | ⁿ√(S₁×S₂×...×Sₙ) | **满足对称性**：GM(A/B) = 1/GM(B/A) |

**关键性质**：几何均值是唯一满足"正反向比较互为倒数"的汇总指标。

```
Geometric Mean = (S₁ × S₂ × ... × Sₙ)^(1/N)
```

**推导**：对加速比取对数后求均值再取指数 — 本质是在对数空间做算术均值。

### 2. Speedup 的正确计算

```
Speedup = Time_old / Time_new

# 多个 benchmark 的汇总：
Overall Speedup = GM(Speedup₁, Speedup₂, ..., Speedupₙ)
                = (Speedup₁ × Speedup₂ × ... × Speedupₙ)^(1/N)
```

**常见错误**：对每个 benchmark 算 (TimeA - TimeB)/TimeA 然后取算术均值 — 这会高估或低估真实性能差异。

### 3. Benchmark 选择原则

| 原则 | 含义 |
|------|------|
| **代表性** | 覆盖目标工作负载的典型操作 |
| **多样性** | 包含不同特征的程序（compute-bound / memory-bound / branch-heavy） |
| **可重现** | 明确定义输入、编译选项、运行环境 |
| **公平性** | 相同编译器优化等级、相同库版本 |
| **时效性** | 定期更新（SPEC 每 3-5 年一次） |

### 4. 常见的量化错误（避坑指南）

1. **挑选有利 benchmark（Cherry-picking）**：只展示自己擅长的 workload
2. **不对称约束**：对手限制频率/带宽，自己不限
3. **相对 vs 绝对**：说"提升了 50%"但不给绝对值（可能从 1ms → 0.67ms，无关紧要）
4. **忽略方差**：只报均值不报置信区间，可能差异不显著
5. **基准过时**：和 5 年前的设计比，意义有限
6. **Roofline 误用**：用错误的 Roofline 模型（算力或带宽参数不准）

## 🧪 练习题（约 30-60 分钟）

### 基础题

**Q1**：给定 5 个 benchmark 的加速比 [1.2, 1.5, 0.9, 2.1, 1.8]，计算几何均值。

> **解**：
> GM = (1.2 × 1.5 × 0.9 × 2.1 × 1.8)^(1/5)
> = (1.2 × 1.5 = 1.8; 0.9 × 2.1 = 1.89; 1.8 × 1.89 = 3.402)
> 等等，重算：
> 1.2 × 1.5 = 1.8
> 1.8 × 0.9 = 1.62
> 1.62 × 2.1 = 3.402
> 3.402 × 1.8 = 6.1236
> GM = 6.1236^(1/5) = 6.1236^0.2
> ln(6.1236) = 1.8113
> 1.8113 / 5 = 0.3623
> e^0.3623 ≈ 1.4365
> **GM ≈ 1.44**

**对比算术均值**：(1.2+1.5+0.9+2.1+1.8)/5 = 7.5/5 = 1.50

注意算术均值（1.50）比几何均值（1.44）更高 — 这不是巧合，算术均值总是 ≥ 几何均值（AM-GM 不等式）。

### 进阶题

**Q2**：处理器 A 在 5 个 benchmark 上相比处理器 B 的加速比为 [1.3, 1.1, 0.8, 1.7, 1.2]。而处理器 B 相比 A 的"加速比"应该是什么？验证几何均值的对称性。

> B 相比 A 的加速比 = [1/1.3, 1/1.1, 1/0.8, 1/1.7, 1/1.2]
> = [0.769, 0.909, 1.25, 0.588, 0.833]
> GM_A/B ≈ 1.193
> GM_B/A ≈ 1/1.193 ≈ 0.838 ✓
> **对称性验证通过**：GM(A/B) × GM(B/A) = 1

### 研究分析题

**Q3**：假设你读到一篇论文声称他们的 NoC 设计比 baseline 平均快 2.3×。你会问哪些问题来验证这个结论的可靠性？

> **检查清单**：
> 1. "平均"是几何均值还是算术均值？（如果算术均值，可能被极端值拉高）
> 2. baseline 是什么？是最新设计还是 5 年前的？
> 3. 两个设计的频率、工艺节点、面积预算是否一致？
> 4. Benchmark 是否覆盖了不同 traffic pattern（uniform random, transpose, hotspot）？
> 5. 有没有报方差/置信区间？2.3× 是否显著？
> 6. 测量方法：仿真器是否校准过？周期精确仿真还是近似模型？
> 7. 有没有 omit 不利的结果？（文件抽屉效应）
> 8. 网络规模是否一致？（4×4 mesh 和 8×8 mesh 性能特征差异巨大）

### 思考题（与 WSE/NoC 研究关联）

**Q4**：如果你要评估 WSE-3 在 LLM 推理上的性能，你会选择什么 benchmark？如何设计公平的对比实验（vs NVIDIA H100）？

> **思路**：
> - **Benchmark**：MLPerf Inference（GPT-J, LLaMA-70B, 等），覆盖不同模型大小
> - **公平约束**：相同精度（FP16/BF16）、相同 batch size（或报告完整 latency-throughput 曲线）、相同模型
> - **指标**：tokens/s（吞吐量）、ms/token（延迟）、tokens/s/W（能效）、tokens/s/mm²（面积效率）
> - **汇总**：几何均值跨模型汇总
> - **注意**：WSE 的优势在 weight-stationary 大模型推理，小模型可能看不出优势 — 需要报告完整可扩展性曲线

## 🔗 与 WSE/NoC 研究的关联

### 今天的方法论 = 你未来论文的根基

1. **Benchmark 设计**：做 NoC 研究时，traffic pattern 选择直接决定结论。synthetic（uniform/transpose/bit-reversal）vs real application traces 会给出截然不同的结果。

2. **几何均值汇总**：你在论文里展示"平均延迟降低 30%"时，审稿人第一个看的就是你用什么均值。

3. **公平比较**：对比 NoC 拓扑时，如果你的设计用 3 个虚拟通道而 baseline 只有 1 个，这不是架构创新，是资源不公平分配。

4. **Roofline 模型预演**：明天不会讲，但量化方法论为后续 Roofline 分析打下基础 — 你需要知道什么时候"瓶颈是算力"vs"瓶颈是带宽"。
