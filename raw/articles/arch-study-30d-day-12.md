## 🔑 核心概念（必须掌握）

### 1. 指令窗口的组成

```
指令窗口 (Instruction Window) = ROB + Issue Queue(s)

  ┌──────────────────────────────────────────┐
  │            Reorder Buffer (ROB)            │
  │  ┌────┬────┬────┬────┬────┬────┬────┐    │
  │  │ #1 │ #2 │ #3 │ #4 │ #5 │ #6 │... │    │  ← 按序提交
  │  └────┴────┴────┴────┴────┴────┴────┘    │
  └──────────────────────────────────────────┘
  ┌──────────────────────────────────────────┐
  │          Issue Queue(s) (Wakeup/Select)   │
  │  ┌────┬────┬────┬────┬────┐               │
  │  │ Q1 │ Q2 │ Q3 │ Q4 │... │  ← 乱序执行  │
  │  └────┴────┴────┴────┴────┘               │
  └──────────────────────────────────────────┘

ROB 大小 = 指令窗口大小（决定能"看到"多远的 ILP）
Issue Queue 大小 = 同时等待操作数的指令数（决定调度灵活性）
```

**两个关键延迟（决定窗口的实用性）：**
- **Wakeup 延迟**：一条指令完成后"唤醒"等待它的指令所需时间
- **Select 延迟**：从就绪队列中选出可发射指令所需时间

### 2. 指令窗口大小 vs IPC 的量化关系

```
关键结论（Palacharla et al. 1997 + 后续研究）：

指令窗口大小    理论 IPC（理想处理器）    实际 IPC（考虑电路延迟）
     16              ~2.0                    ~1.8
     32              ~2.5                    ~2.1
     64              ~3.0                    ~2.4
    128              ~3.5                    ~2.6
    256              ~4.0                    ~2.7  ← 边际收益 < 4%
    512              ~4.3                    ~2.75 ← 几乎无收益
   1024              ~4.5                    ~2.78 ← 电路延迟吃掉了增益

转折点：窗口 ~128-256 之后，IPC 提升被电路延迟和功耗成本抵消
```

**为什么收益递减？**
- 真实代码中的 ILP 是有限的（数据依赖链限制了并行度）
- 窗口增大会增加 wakeup/select 的延迟（O(N) 或 O(N²) 电路复杂度）
- 更大的窗口 → 更大的重命名表 → 更长的访问延迟

### 3. 寄存器重命名深入

#### 为什么要重命名？

```
假依赖 (Name Dependence)：
  I1: ADD R2, R1, R3    // 定义 R2
  I2: SUB R4, R2, R5    // 用 R2（真依赖 → 必须等 I1）
  I3: MUL R2, R6, R7    // 重新定义 R2（WAR 假依赖）
  I4: DIV R8, R2, R9    // 用 R2（WAW 假依赖）

WAR (Write-After-Read)：I3 不能在 I2 之前完成（否则 I2 读到新值）
WAW (Write-After-Write)：I4 不能读到 I3 之前的 R2 值

通过重命名：R2 → P2(I1), P2'(I3)
  I1: ADD P2, P1, P3
  I3: MUL P2', P6, P7   ← 不同物理寄存器，消除 WAR/WAW
```

#### 重命名的两种实现方式

**(a) 基于保留站 (Reservation Station) — Tomasulo 原始设计**
```
- 每个保留站保存操作数（不在寄存器中）
- 指令发射到保留站时，从寄存器读走当前值或标签
- 优点：简单
- 缺点：操作数在保留站间复制，浪费面积；多发射时总线复杂
```

**(b) 基于物理寄存器 (Physical Register File) — 现代处理器**
```
架构寄存器 (ARF)：R0-R31 (RISC-V) / RAX-R15 (x86)
物理寄存器 (PRF)：P0-P127 (通常 128-256 个)

重命名表 (Register Alias Table / RAT)：
  ┌──────────┬────────────┐
  │ 架构寄存器 │ 物理寄存器  │
  ├──────────┼────────────┤
  │ R1       │ P5         │
  │ R2       │ P12        │  ← 当前映射
  │ R3       │ P7         │
  │ ...      │ ...        │
  └──────────┴────────────┘

工作流程：
  1. Issue：新指令的目标 → 分配新物理寄存器（从 Free List）
  2. Execute：通过 RAT 查找源操作数对应的物理寄存器
  3. Commit：物理寄存器正式"成为"架构寄存器
  4. Free：旧映射的物理寄存器返回 Free List
```

### 4. Free List 管理

```
Free List：未被使用的物理寄存器集合

  初始状态：PRF 有 N 个物理寄存器，ARF 需要 M 个（M < N）
  可用于重命名的 = N - M 个

  ┌─────────────────────────────────────┐
  │  Physical Register File (PRF)        │
  │  P0  P1  P2  ...  P_M  P_M+1 ... P_N │
  │  ├───ARF 映射──┤├── Free List ──┤   │
  └─────────────────────────────────────┘

分配周期 (每条指令)：
  1. 从 Free List 取一个 P_new
  2. RAT[dst] ← P_new（旧映射 P_old 记录在 ROB 中）
  3. 指令执行完成后，结果写入 P_new

释放周期 (提交时)：
  1. 指令 commit → 旧映射 P_old 可以回收
  2. P_old 加入 Free List

约束：Free List 不能空（否则 stall 重命名阶段）
  → 需要的物理寄存器数 ≈ ROB 大小 + ARF 大小
```

### 5. 指令窗口设计的核心矛盾

```
           更多 ILP ←────────────→ 实用性
                ↑                        ↑
         大窗口（看到更多指令）    电路延迟 + 功耗 + 面积

面积成本分解（典型 4-way 超标量）：
  ROB (128 entries)         ~2 mm²
  Issue Queue (32-64)       ~1.5 mm²
  PRF (128-256)             ~2.5 mm²
  Rename Table              ~0.5 mm²
  Wakeup/Select Logic       ~1.5 mm²
  ──────────────────────────────────
  Total                     ~8 mm²   （在 ~100 mm² 的核心中占 ~8%）

功耗：乱序引擎可占核心功耗的 20-30%
```

## 🧪 练习题（约 30-60 分钟）

### 基础题

**Q1**：一个处理器有 32 个架构寄存器 (R0-R31)，ROB 大小为 64。最少需要多少个物理寄存器才能保证重命名不会 stall？

> 答：需要的物理寄存器数 ≥ ROB 大小 + 架构寄存器数 = 64 + 32 = 96
>
> 解释：ROB 中的 64 条指令每条可能定义一个新寄存器（需要 64 个额外物理寄存器），同时 32 个架构寄存器需要 32 个"已提交"的物理寄存器。所以 PRF ≥ 96。

**Q2**：给定以下代码序列，标注所有依赖关系（RAW/WAR/WAW），并展示寄存器重命名后的结果：
```
I1: ADD  R2, R1, R3
I2: SUB  R4, R2, R5
I3: MUL  R2, R6, R7
I4: ADD  R5, R2, R8
I5: SUB  R2, R9, R10
```

> 答：
> 依赖分析：
> - I1→I2: RAW (R2) ✓ 真依赖
> - I1→I3: WAW (R2) — I3 重定义 R2
> - I2→I3: WAR (R2) — I2 读 R2，I3 写 R2
> - I3→I4: RAW (R2) ✓ 真依赖
> - I3→I5: WAW (R2) — I5 重定义 R2
> - I4→I5: WAR (R2) — I4 不读 R2，无此依赖
>   实际上 I4 读 R5，I1 不写 R5，I3 不写 R5 → I4 的 R5 是初始值
>   修正：I4 读 R2 和 R8，I3 写 R2 → I3→I4 RAW (R2)
>   I4 读 R5（初始值），无假依赖
>
> 重命名（假设初始 R1=P1, R2=P2, R3=P3, R5=P5, R6=P6, R7=P7, R8=P8, R9=P9, R10=P10）：
> ```
> I1: ADD  P11, P1, P3      // R2 → P11
> I2: SUB  P12, P11, P5     // R4 → P12 (等 P11 就绪)
> I3: MUL  P13, P6, P7      // R2 → P13 (不等 I2！WAW/WAW 消除)
> I4: ADD  P14, P13, P8     // R5 → P14 (等 P13 就绪)
> I5: SUB  P15, P9, P10     // R2 → P15 (不等 I3！WAW 消除)
> ```
> 重命名后，I3 不再需要等 I2 读完 R2。只剩 RAW 真依赖链：I1→I2, I3→I4。

### 进阶题

**Q3**：根据 Palacharla et al. (1997) 的研究，指令窗口从 64 增加到 256，理论 IPC 提升约 33%（从 ~3.0 到 ~4.0），但实际 IPC 仅提升约 12.5%（从 ~2.4 到 ~2.7）。请解释差异的原因。

> 答：
> 理论模型假设：
> - Wakeup/Select 延迟 = 0
> - 重命名表访问延迟 = 0
> - Issue Queue 查找延迟 = 0
>
> 实际中：
> 1. **Wakeup/Select 延迟非线性增长**：窗口从 64→256，关联比较电路的延迟可能翻倍，导致时钟频率降低或需要多周期操作
> 2. **PRF 访问延迟增大**：256 个物理寄存器的文件比 128 个更大，读/写延迟增加
> 3. **功耗约束**：更大窗口消耗更多功耗，可能触发降频
> 4. **真实 ILP 有限**：即使窗口无限大，真实程序的依赖链也限制了可用并行度（通常 < 4-5）
>
> 核心教训：体系结构设计中，"理论提升"和"实际提升"的差距往往来自电路实现的物理约束。

### 思考题（与 WSE/NoC/NPU 研究关联）

**Q4**：Cerebras WSE-3 的 SLA 核心是指令窗口 = 1 的极端情况（顺序、单发射、无重命名）。对比：
- 一个 SLA 核心的 IPC 上限是多少？
- WSE 用 900,000 个 IPC=1 的核心 vs 传统 CPU 用 64 个 IPC=3 的核心，在什么工作负载下 WSE 赢？什么工作负载下 CPU 赢？

> 提示：
> - SLA 核心 IPC ≤ 1，但 900K 核 × IPC 1 = 900K 操作/周期
> - 64 核 CPU × IPC 3 = 192 操作/周期
> - WSE 赢的条件：工作负载可以分解为大量独立、规则的运算（矩阵乘、卷积）
> - CPU 赢的条件：工作负载有复杂控制流、不规则访存、需要大窗口来发掘并行性
> - 这就是"大量简单核" vs "少量复杂核"的经典架构权衡

## 🔗 与 WSE / NoC / NPU 研究的关联

| 概念 | 传统超标量 CPU | WSE SLA 核心 | NPU PE |
|------|---------------|-------------|--------|
| 指令窗口 | 128-256 | 1（顺序执行） | 1（数据流驱动） |
| 寄存器重命名 | 128-256 物理寄存器 | 不需要 | 不需要 |
| ILP 发掘方式 | 硬件乱序 | 编译器静态调度 | 空间映射 |
| 面积效率 | ~8% 面积给乱序引擎 | 0% → 全部给计算和 SRAM | 0% → 全部给 MAC 单元 |
| 功耗效率 | 乱序引擎占 20-30% 功耗 | 100% 功耗给有效计算 | ~100% 给有效计算 |

**核心洞察**：指令窗口和重命名是通用 CPU 为了"自动发现 ILP"而付出的巨大代价。WSE/NPU 的设计哲学是——**如果工作负载的并行性可以被程序员/编译器显式表达，就完全不需要这些硬件**。

**与核内同步的关联**：在传统多核中，核间同步原语（如 spinlock）的行为受乱序执行影响——指令重排可能导致锁操作的顺序不符合预期，需要 memory barrier。WSE 的顺序执行天然保证了指令顺序，使得同步逻辑更简单、更可预测。这对 NoC 协议设计（如请求-响应顺序保证）是一个简化。
