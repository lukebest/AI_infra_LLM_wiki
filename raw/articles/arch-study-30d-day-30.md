### 2. 5 个核心问题（30 天所有知识的"根"）

> 如果只能问 5 个问题来检验 30 天学习，这 5 个问题能覆盖 80% 的核心内容。

**Q1：性能从哪里来？**
```
性能 = IC × CPI × Clock Cycle Time
     = (Instruction Count) × (Cycles Per Instruction) × (Clock Cycle Time)

→ 30 天的所有优化都围绕这三个因子：
  - 减少 IC：编译器优化、ISA 设计、算法改进
  - 降低 CPI：流水线、OoO、分支预测、Cache、预取
  - 缩短 T：工艺、流水线深度、并行化

→ 三个因子相互制约（不是独立优化空间）：
  - 频率 ↑ → 流水线更深 → 分支惩罚 ↑ → CPI ↑
  - IC ↓（复杂指令）→ CPI ↑（复杂指令多周期）
  - 并行度 ↑ → 通信开销 ↑ → 实际 CPI ↑（Amdahl）
```

**Q2：瓶颈在哪里？**
```
Roofline 模型：
  Attainable Perf = min(Peak Compute, BW × AI)
  - 拐点 (Ridge Point) = Peak Compute / BW
  - AI < 拐点 → memory-bound（带宽瓶颈）
  - AI > 拐点 → compute-bound（算力瓶颈）

Amdahl 定律：
  Speedup = 1/((1-f) + f/S)
  → 找到 f 小的部分（串行部分）就是瓶颈

→ 例子：WSE-3 的 Ridge Point ≈ 6 FLOPs/Byte
  - GEMM (AI=128) → compute-bound
  - LLM decode (AI≈2) → memory-bound
  - 这是 LLM 推理在 WSE 上能跑得极快的原因
```

**Q3：数据怎么搬？**
```
存储层次 = 时间局部性 + 空间局部性的利用

  CPU Registers (1 cycle)
    ↓ 几十 ns
  L1 Cache (4 cycles, ~32 KB)
    ↓ 几 ns
  L2 Cache (12 cycles, ~256 KB)
    ↓ 几 ns
  L3 / LLC (40 cycles, ~MB)
    ↓ 几十 ns
  DRAM (200 cycles, ~GB)
    ↓ μs
  SSD / NVMe (10-100 μs)
    ↓ ms
  Network / RDMA (~10-100 μs)
    ↓ s
  Cold Storage

关键数字：
  - 寄存器 vs DRAM: 100,000× 延迟差
  - 片上 (WSE 21 PB/s) vs 片外 (HBM 1 TB/s): 20,000× 带宽差
  → 数据搬运是体系的"沉默杀手"
```

**Q4：并行怎么排？**
```
并行 = 空间并行 + 时间并行

  空间并行（同时做多件事）：
    - ILP（指令级）：超标量 + OoO
    - DLP（数据级）：SIMD, SIMT, 脉动阵列
    - TLP（线程级）：多核, 多线程, GPU

  时间并行（重叠）：
    - 流水线
    - 乱序执行
    - 通信-计算重叠

  并行的代价：
    - 同步开销（MCS lock, barrier, fence）
    - 通信开销（AllReduce, All-to-All）
    - 共享资源冲突（cache line ping-pong, 带宽争用）
    - 硬件复杂度（一致性协议, 路由器, QoS）

→ WSE 的"反并行哲学"：
  - 不用 OoO（不挖 ILP）
  - 不用 Cache 一致性（不用共享内存）
  - 不用虚拟内存（不用 TLB）
  - 换：900K 个简单 PE × 数据流映射 → 极致并行
```

**Q5：怎么量化评价？**
```
体系结构的"研究伦理" = 公平 + 透明 + 可复现

  公平 (Fair Comparison)：
    - 相同工艺节点
    - 相同面积 / 功耗预算
    - 相同编译器 / 软件栈
    - 相同 baseline 调优程度

  透明 (Transparency)：
    - 报告所有相关指标，不只挑"漂亮"的
    - 报告 baseline 的实现细节
    - 报告敏感性分析（不同 workload 类别）

  可复现 (Reproducibility)：
    - 提供代码 / 配置 / 数据
    - 提供详细实验步骤
    - 报告几何均值 + 标准差（不只是 GM）

  → Hennessy & Patterson 的"研究方法论"原则：
    "Garbage in, garbage out" — 没有好 benchmark 就没有好结论
```

### Q1：CPU 性能公式的三个因子是什么？它们之间如何相互影响？

**参考答案**：
```
CPU Time = IC × CPI × Clock Cycle Time

三个因子：
1. IC (Instruction Count): 指令数
   - 决定因素：算法、编译器、ISA
   
2. CPI (Cycles Per Instruction): 每条指令周期数
   - 决定因素：微架构（流水线、Cache、OoO、分支预测）
   
3. Clock Cycle Time: 时钟周期
   - 决定因素：工艺、流水线深度、关键路径

相互影响（不是独立优化空间）：
- 频率 ↑（T ↓）→ 流水线更深 → 分支惩罚 ↑ → CPI ↑
- IC ↓（复杂指令）→ 单条指令 CPI ↑
- 并行度 ↑ → 通信开销 ↑ → 实际 CPI ↑
- 优化 Cache → IC ↑（cache 友好代码可能指令数变多）

→ 体系结构的核心是"权衡"（trade-off），不是"独立优化"
```

### Q2：Amdahl 定律和 Gustafson 定律的区别？各自适用于什么场景？

**参考答案**：
```
Amdahl 定律（固定负载）：
  Speedup(N) = 1 / ((1-f) + f/N)
  假设总负载不变 → 串行部分是固定开销
  适用：固定问题规模下的加速比分析
  例子：科学计算（问题规模固定）

Gustafson 定律（可扩展负载）：
  Speedup(N) = N - α(N-1)    [α = 串行占比]
  假设串行时间不变 → 负载随 N 增大
  适用：问题规模可扩展的并行
  例子：机器学习（用更大 batch 训练更大模型）

关键区别：
- Amdahl: 串行部分是"绝对天花板"
- Gustafson: 串行部分占比固定，但绝对时间不变
  
→ 实际系统通常介于两者之间
→ Luke 的 WSE 研究更适合 Amdahl（单 wafer 物理上限）
→ 分布式 AI 训练更适合 Gustafson（可扩展 batch/model）
```

### Q3：描述 Tomasulo 算法的完整流程

**参考答案**：
```
Tomasulo 算法：动态调度实现乱序执行
核心思想：用硬件（保留站）实现寄存器重命名 + 乱序发射

三个阶段：
1. Issue (发射)
   - 从指令队列取指令
   - 分配保留站（Reservation Station）
   - 读寄存器值（如果就绪）或记录依赖
   - 寄存器重命名：消除 WAR/WAW 假依赖

2. Execute (执行)
   - 等待所有操作数就绪
   - 操作数就绪后开始执行
   - 可能多周期（FP 单元、分支预测失败取消等）

3. Write Result (写回)
   - 执行完成后，通过 Common Data Bus (CDB) 广播结果
   - 所有等待该结果的保留站捕获值
   - 释放保留站

关键组件：
- 保留站 (Reservation Station)：保存操作数 + 操作 + 状态
- 公共数据总线 (CDB)：广播执行结果
- Load/Store 单元：处理内存访问
- FP 寄存器：32 个 × 2 读 1 写

优点：
- 自动消除 WAR/WAW 假依赖
- 动态调度（运行时找 ILP）
- 不需要编译器配合

局限：
- 保留站数量有限（典型 16-64）
- CDB 是单点瓶颈
- 精确中断恢复困难
→ 后来被 ROB（Reorder Buffer）方案替代，但仍保留保留站思想
```

### Q4：MESI 协议中四种状态的含义和转换条件

**参考答案**：
```
MESI = Modified / Exclusive / Shared / Invalid

四个状态：
1. M (Modified)：该 cache line 是唯一副本，且已被修改（与内存不一致）
   - 权限：可读可写
   - 内存状态：过期

2. E (Exclusive)：该 cache line 是唯一副本，但与内存一致
   - 权限：可读可写
   - 内存状态：最新

3. S (Shared)：该 cache line 可能有多个副本，与内存一致
   - 权限：只读
   - 内存状态：最新

4. I (Invalid)：该 cache line 无效（不存在或已废弃）

转换条件（简化版）：
- 本地读 (PrRd)：
  - I → 发送 BusRd → S (其他有副本) 或 E (没有副本)
- 本地写 (PrWr)：
  - S → 发送 BusUpgr → M
  - E → M (直接)
  - I → 发送 BusRdX → M
- 嗅探 BusRd（其他核读）：
  - M → 写回内存 → S
  - E → S
  - S → S (不变)
- 嗅探 BusRdX（其他核写）：
  - M → 写回内存 → I
  - E → I
  - S → I

→ MESI 是 snooping 协议的经典实现
→ 目录式协议 (Directory) 在大规模多核中更可扩展
→ WSE 不需要 MESI：因为没有共享内存
```

### Q5：2D Mesh vs Fat Tree vs Dragonfly 各自的优缺点

**参考答案**：
```
┌────────────┬─────────────────┬─────────────────┬─────────────────┐
│ 维度       │ 2D Mesh          │ Fat Tree         │ Dragonfly        │
├────────────┼─────────────────┼─────────────────┼─────────────────┤
│ 双分带宽   │ n (低)          │ N/2 (高)        │ ~N/2 (高)       │
│ 直径       │ 2(n-1) (大)     │ 2·log_k(N)      │ ≤ 3 (小)        │
│ 节点度     │ 4 (低)          │ k (高)          │ p (高)          │
│ 链路成本   │ 低              │ 高              │ 中              │
│ 路由       │ 简单 (DOR)      │ 中等 (上/下路)  │ 复杂 (组内+组间)│
│ 容错       │ 多路径          │ 多路径          │ 局部多路径      │
│ 适用规模   │ 数十到数百核    │ 数千到数万核    │ 数千到十万核    │
│ 典型应用   │ 片上 NoC, 芯片  │ 数据中心 Spine  │ Cray, 天河      │
│            │ WSE (Mesh)     │ Fat-tree       │ 超级计算机       │
└────────────┴─────────────────┴─────────────────┴─────────────────┘

WSE 选择 2D Mesh 的原因：
1. 物理实现简单（VLSI 布线友好）
2. 拓扑可扩展（增加 PE = 增加网格边）
3. DOR 路由简单（先 X 后 Y，硬件简单）
4. 容错容易（每个 PE 路由器独立）
5. 制造容错（缺陷 PE 通过 Route-around 绕过）
6. 软件友好（编程模型简单：x,y 坐标）

→ Mesh 的缺点（双分带宽低）在 WSE 上被缓解：
  - LLM 推理的 all-to-all 流量是问题
  - Luczynski 的 FRED/FREDR 在 Mesh 上做优化（Day 28）
  - 多 wafer 互连 (SwarmX) 可能用 Dragonfly-like 拓扑
```

### Q6：数据中心 AllReduce 的通信复杂度是多少？

**参考答案**：
```
Ring AllReduce (N workers, D bytes):
  - 通信总量 (每 worker): 2(N-1) × D/N ≈ 2D
  - 总步数: 2(N-1)
  - 单步传输量: D/N
  - 时间: 2(N-1) × (D/N) / B_link = 2D(N-1)/(N·B) ≈ 2D/B (与 N 无关！)

Tree AllReduce (Binary Tree):
  - 通信总量: D × log₂(N)
  - 总步数: log₂(N)
  - 单步传输量: D (根) / D/2^k (中间层)
  - 时间: 2·log₂(N) × D / B

对比：
- Ring: 总传输量 2D（小消息友好，与 N 无关）
- Tree: 总步数 log₂(N)（小步数，延迟敏感时友好）

→ 实际系统 (NCCL) 通常用 Ring + Tree 混合：
  - 节点内 (NVLink): Tree (低延迟)
  - 节点间 (IB/RoCE): Ring (高带宽)

Ring AllReduce 的关键洞察：
  - 2D bytes per worker, regardless of N
  → 大模型分布式训练 = 大 D → 通信时间随 D 线性增长
  → 加速模型规模 = 加速通信负担（这就是为什么 MoE / 量化 / 压缩重要）

256 GPU GPT-3 训练 (FP16, 175B 参数):
  T_compute ≈ 4 ms/step (1 batch, 256 GPU)
  T_comm ≈ 500-5000 ms/step (AllReduce 通信)
  → 通信/计算比 = 100-1000× （训练速度由通信决定）
```

### Q7：Roofline 模型如何评估加速器性能？拐点 (Ridge Point) 的含义？

**参考答案**：
```
Roofline 模型：
  Attainable Performance = min(Peak Compute, Peak BW × Arithmetic Intensity)
  - x 轴: Arithmetic Intensity (ops/byte)
  - y 轴: Performance (ops/sec)

两个边界：
1. 水平线: Peak Compute (GFLOPS, TOPS) — 算力天花板
2. 斜线: Peak BW × AI — 带宽天花板（斜率 = Peak BW）

拐点 (Ridge Point):
  Ridge Point = Peak Compute / Peak BW
  - 单位: ops/byte (或 FLOPs/Byte)
  - 含义: 当 AI = 拐点时，算力和带宽都达到上限（最佳工作点）

如何使用：
1. 画出加速器的 Roofline（已知 Peak Compute 和 Peak BW）
2. 计算目标 workload 的 AI (ops/byte)
3. 判断瓶颈：
   - AI < 拐点 → memory-bound（在斜线段）→ 优化带宽/数据复用
   - AI > 拐点 → compute-bound（在线段）→ 优化算力/流水线

WSE-3 的 Roofline (Day 26):
  Peak Compute = 125 PFLOPS (FP16)
  Peak BW = 21 PB/s (片上 SRAM)
  Ridge Point = 125e15 / 21e15 = ~6 FLOPs/Byte

判断：
- GEMM (AI = 128) → compute-bound → 优化 PE 利用率
- LLM decode (AI ≈ 2) → memory-bound → 优化权重加载/数据复用
- Layer Norm (AI ≈ 1) → memory-bound → 几乎用不上算力

→ Roofline 是"性能诊断的第一性工具"
→ 任何新加速器设计都应先画 Roofline，再讨论优化
```

### Q8：WSE 的 2D Mesh NoC 相比传统 NoC 的核心优势是什么？为什么不需要复杂拓扑？

**参考答案**：
```
WSE 2D Mesh NoC 的核心优势：

1. 物理可实现性
   - 2D Mesh 在 VLSI 上布线规则简单（每个 PE 4 邻居）
   - 不需要复杂路由器（先 X 后 Y 的 DOR 路由）
   - 光罩可容纳，不需要长距离线

2. 可扩展性
   - 增加 PE 数 = 增加网格边（线性扩展）
   - 面积利用率高（mesh 紧凑）
   - 与良率模型匹配（小 PE × 大量 = 容错友好）

3. 容错性
   - 物理缺陷 → Route-around 绕过
   - 运行时错误 → Fail-in-place（用冗余 PE）
   - Mesh 多路径性质提供自然容错

4. 软件友好
   - 编程模型简单（x, y 坐标直接映射）
   - CSL/SpaDA 等数据流语言直接编译到 mesh
   - 调试简单（PE 编号就是地址）

5. 带宽密度极高
   - 每个 PE 都有 4 个网络端口 → 总带宽 = N × 度 / 2 × B
   - 21 PB/s 片上带宽（vs HBM 1 TB/s → 20,000× 优势）

为什么不需要复杂拓扑（Fat Tree / Dragonfly）：

1. 通信模式匹配
   - WSE 设计目标是 compute-bound AI workload（GEMM, GEMV）
   - 通信模式：nearest-neighbor 为主（数据流）
   - all-to-all 流量少（与传统分布式不同）

2. 物理规模限制
   - 单一 wafer 直径 300mm，2D Mesh 已经能容纳 900K PE
   - 更复杂拓扑的物理实现代价高于收益

3. 面积预算
   - 每个 PE 仅有 ~50KB SRAM + 简单 ALU
   - 复杂路由器占用的晶体管 = 减少 PE 数量
   - PE 数量 ↑ 比 NoC 带宽 ↑ 更重要

4. 容错机制
   - Route-around 已经在物理层处理缺陷
   - 不需要 Dragonfly 的复杂组内/组间路由

→ Mesh + 大量 PE + 数据流 = WSE 的"道"
→ 与传统多核芯片的根本区别：目标 workload 不同
```

### Q9：乱序执行如何提升 IPC？有哪些硬件限制？

**参考答案**：
```
乱序执行 (OoO) 提升 IPC 的机制：

理想 CPI = 1（每周期完成一条指令）
实际 CPI > 1 的原因：
- 数据依赖（必须等前一条指令的结果）
- 结构冒险（资源冲突）
- 控制依赖（分支后的指令不知道是否执行）

OoO 如何解决：
1. 寄存器重命名：消除 WAR/WAW 假依赖（保留站 + 映射表）
2. 动态调度：保留站按数据就绪顺序发射（不等程序顺序）
3. 指令窗口：让更多指令同时"在飞"，找更多 ILP

IPC 提升上限：
- 理想 IPC = 指令窗口大小 / 平均数据依赖链长度
- 典型实际：OoO 提升 IPC 1.3-1.8×（vs in-order）

硬件限制：

1. 指令窗口大小
   - ROB: 128-512 项
   - IQ: 32-128 项
   - 物理寄存器: 128-256 个
   → 窗口小 = 看不到远距离 ILP
   → 窗口大 = 时序/功耗压力

2. 保留站 / IQ 复杂度
   - 唤醒逻辑（CAM-based）复杂度和端口数
   - 选择逻辑（age matrix）功耗高
   - 典型：发射宽度 4-6（很少 > 8）

3. 重命名表
   - 物理寄存器文件大小影响访问时间
   - Free list 管理复杂度
   - Rename 阶段可能成为流水线瓶颈

4. 分支预测错误
   - 错误时必须 flush 流水线上的乱序指令
   - 浪费功耗和带宽
   - → 限制了可用的"在飞指令数"

5. 内存依赖
   - Load/Store 顺序难预测
   - Load-Use 冒险难以完全消除
   - → 即使 OoO，遇到 cache miss 仍然停顿

6. 功耗
   - OoO 的唤醒/选择逻辑占处理器功耗 30-50%
   - 时钟频率难以提升

→ OoO 收益边际递减
→ 现代趋势：前台 OoO（性能）+ 后台 in-order 小核（能效）
→ WSE 直接放弃 OoO（用 900K 简单 PE 替代）
```

### Q10：量化研究中，如何确保性能比较的公平性？

**参考答案**：
```
量化研究中的公平比较原则（Hennessy-Patterson 方法论）：

1. 相同工艺节点 (Same Technology Node)
   - 不要拿 7nm 设计 vs 14nm baseline
   - 至少要按面积/晶体管数归一化

2. 相同资源预算
   - 相同面积、相同功耗、相同晶体管数
   - 或归一化到 GFLOPS/Watt, GFLOPS/mm²

3. 相同编译器 / 软件栈
   - 不要 baseline 用 -O0，新设计用 -O3
   - 至少要在同一编译选项下对比

4. 相同 baseline 调优程度
   - 给 baseline 同样的调优时间
   - baseline 是否用了厂商最新库（如 cuDNN, NCCL）

5. 多个 benchmark
   - 不要只跑一个程序就下结论
   - 至少 5-10 个，覆盖不同 workload 类别
   - 用几何均值（不用算术均值）汇总

6. 详细报告
   - 不只报告"平均加速比"
   - 报告：每个 benchmark 结果、置信区间、敏感性分析
   - 报告：失败的 case（不是只报"我们更好"）

7. 多种性能指标
   - 延迟 (latency)
   - 吞吐量 (throughput)
   - 能耗 (energy)
   - 面积 (area)
   - 成本 (cost)
   - → 多目标 Pareto 前沿

8. 工作负载相关性
   - 用真实的 workload（不是 toy benchmark）
   - 行业标准：SPEC, MLPerf, PARSEC
   - 自定义 workload 要公开

9. 复现性
   - 公开代码 / 配置 / 数据
   - 公开实验环境
   - 提供详细步骤

10. 批判性
    - 自报失败 case
    - 自报局限性
    - 讨论"什么时候不工作"
    - 学术诚信 > 论文好看

→ "Garbage in, garbage out" — 没有好 benchmark 就没有好结论
→ Day 6 的统计方法（几何均值、置信区间）是基础
```
