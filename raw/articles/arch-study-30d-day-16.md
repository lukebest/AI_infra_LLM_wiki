### 1. 一段代码在现代 CPU 上的完整旅程

```

    a[i] = b[i] + c[i];
    d[i] = a[i] * e[i];
  }

这条代码在现代超标量处理器（如 Intel Golden Cove）上的执行过程：

┌─────────────────────────────────────────────────────────────┐
│  前端 (Frontend)                                              │
│  ┌─────────┐    ┌──────────────┐    ┌──────────────┐        │
│  │ I-Cache │ -> │ 分支预测器    │ -> │ 预译码 +  µop │        │
│  │ 32KB    │    │ (TAGE)       │    │ (复杂指令拆分)│        │
│  └─────────┘    └──────────────┘    └──────────────┘        │
│         ↑              ↑                    ↓                │

│  乱序引擎 (Out-of-Order Engine)                                │
```

### 2. 性能瓶颈的"层级金字塔"

```
                    ┌──────┐
                    │ 频率  │ ← 功耗墙（Dennard 终结后基本停滞）
                    └──────┘
                  ┌──────────┐
                  │  IPC 上限  │ ← 真实程序 ILP ≈ 2-4 (经验值)
                  │  (ILP)   │   理论无限发射也只到 2-3×
                  └──────────┘
                ┌──────────────┐
                │  分支预测精度  │ ← 98% 容易，99.9% 极难
                │  99% 已是顶尖  │
                └──────────────┘
              ┌──────────────────┐
              │  Cache 命中率     │ ← AMAT 主要由 Miss Penalty 决定
              │  L1 ≥ 95%, LLC 80%│
              └──────────────────┘
            ┌──────────────────────┐
            │  DRAM 带宽墙          │ ← 内存墙，是 AI/数据密集型最大瓶颈
            │  ~100 GB/s/通道        │
            └──────────────────────┘
```

**核心洞察**：现代 CPU 的所有传统武器（OoO、Cache、分支预测）都是为了**在功耗墙下榨出更多 IPC**。但面对 AI 工作负载，**内存墙**才是真正的瓶颈——这正是 WSE 押注 SRAM 而非 DRAM 的根本原因。

### 3. "无传统武器"的设计哲学对比

```
┌──────────────────┬────────────────────┬──────────────────────┐
│   传统武器         │  Intel Golden Cove  │  Cerebras WSE-3 PE   │
├──────────────────┼────────────────────┼──────────────────────┤
│ 流水线深度         │ 14+ 级              │ 极浅（指令级）        │
│ 乱序执行          │ 256+ ROB            │ 无                    │
│ 分支预测          │ TAGE (50KB+)        │ 无                    │
│ Cache L1         │ 32-64KB             │ 无（48KB SRAM 直用）  │
│ Cache L2/L3      │ MB 级               │ 无                    │
│ TLB              │ 64-128 项 L1        │ 无                    │
│ 虚拟内存          │ 4 级页表 + MMU      │ 无（直接物理地址）     │
│ 一致性协议         │ MESI/MOESI         │ 无（无共享地址空间）    │
│ 每核面积          │ ~5-8 mm² (估计)      │ 极小，900K PE 在单晶圆  │
│ 每核频率          │ 5+ GHz              │ ~1 GHz               │
│ 编程模型          │ C/C++/任意          │ 数据流 (CSL/SpaDA)    │
└──────────────────┴────────────────────┴──────────────────────┘
```

**WSE 的核心交换**：
- **失去**：通用性 + 单核峰值性能
- **获得**：900K 核的吞吐量 + 21 PB/s 片上带宽 + 确定性延迟

## 🧪 实战练习：纸上模拟完整超标量执行

### 给定代码

```c
// 假设：所有数组都在 L1 Cache 中（理想存储场景）
// 假设：迭代之间无任何数据依赖
for (i = 0; i < 100; i++) {
    a[i] = b[i] + c[i];   // 整数加法
    d[i] = a[i] * e[i];   // 整数乘法
}
```

### 问题 1：列出每条指令的真实数据依赖（RAW）

把循环展开 2 次分析，列出 i=0 和 i=1 的所有指令：

```
# i=0
L1: lw  r1, b[0]      # 加载 b[0]
L2: lw  r2, c[0]      # 加载 c[0]
L3: add r3, r1, r2    # a[0] = b[0] + c[0]
L4: sw  a[0], r3      # 存储 a[0]
L5: lw  r4, a[0]      # 加载 a[0]（依赖 L3/L4 产生）
L6: lw  r5, e[0]      # 加载 e[0]
L7: mul r6, r4, r5    # d[0] = a[0] * e[0]
L8: sw  d[0], r6      # 存储 d[0]
B:  bne r0, r0, loop_end  # 分支 i<100

# i=1
L9:  lw  r11, b[1]
L10: lw  r12, c[1]
...
```

**真实依赖图**（你画出来后应该有这些关键依赖）：

```
RAW 依赖（必须串行）：
  L1 → L3   (b[0] 喂入 add)
  L2 → L3   (c[0] 喂入 add)
  L3 → L4   (add 产生 a[0] 才能存)
  L3 → L5   (a[0] 还要再 load 一次，典型"写后读+重载"反模式)
  L4 → L5   (严格意义上 sw 完成后 lw 才能读到)
  L5 → L7   (a[0] 喂入 mul)
  L6 → L7   (e[0] 喂入 mul)
  L7 → L8   (mul 产生 d[0] 才能存)

名称依赖（WAR/WAW，可通过重命名消除）：
  无（寄存器使用模式简单）

控制依赖：
  B (分支) → 所有下一条循环指令
```

### 问题 2：理想超标量（issue width = 4）下的理论 IPC

**假设**：
- 4 发射，每周期可启动 4 条独立指令
- 加载延迟 4 cycles，乘法延迟 3 cycles，加法延迟 1 cycle
- 无结构冒险（足够的 ALU/LSU/BRU）
- 完美分支预测（循环分支）
- 完美寄存器重命名
- ROB 大小无限

**迭代 0 内的指令排序**（最优调度）：

```
Cycle 1: [L1, L2, L6, B]      # 4 条独立 load + 分支
Cycle 2: [L5 等待 L3]           # L5 依赖 L3, L3 依赖 L1/L2
                              # 但 L6 独立，可以并发
Cycle 3: [L3]                  # add 启动（依赖 L1, L2 已在 cycle 1）
Cycle 4: [L4, L7]              # sw 依赖 L3; mul 依赖 L5, L6
                              # L5 在 cycle 5 才能启动（依赖 L3+L4）
Cycle 5: [L5]                  # lw a[0] 启动
Cycle 7: [L7]                  # mul 启动（依赖 L5 cycle5+4 = 9 ? 不对）

（实际调度更复杂，需要重新计算）
```

**简化答案**：
- 每次迭代核心路径 = `lw b + lw c + add + sw a + lw a + lw e + mul + sw d = 8 µop`
- 关键路径延迟 ≈ `4 (lw b) + max(4,4) + 1 (add) + 4 (sw a=sw 也算 load 端口) + 4 (lw a) + max(4,4) + 3 (mul) + 4 (sw d) = 22 cycles`
- 但因乱序执行，**迭代间可重叠**（i=1 的 load 可与 i=0 的 mul 并发）
- 重叠后：每迭代约 8-10 cycles 完成（取决于端口数）
- **理论 IPC** ≈ 8 µop / 8 cycles = **1.0** （受限于存储端口和长依赖链）

### 问题 3：在序 vs 乱序 vs 理想对比

| 执行方式 | CPI | IPC | 性能差距 |
|---------|-----|-----|----------|
| 5 级流水在序 | ~8.0 | 0.125 | baseline |
| 4 发射在序 | ~5.0 | 0.20 | 1.6× |
| 4 发射乱序 | ~2.5 | 0.40 | 3.2× |
| 4 发射乱序 + 迭代间重叠 | ~1.2 | 0.83 | 6.7× |
| 理论极限（无限制发射） | ~0.4 | 2.5 | 20× |

**关键观察**：
1. **乱序执行带来 ~2× 提升**（从 0.20 → 0.40）
2. **迭代间重叠再带来 ~2×**（从 0.40 → 0.83）
3. **理论极限还有 ~3× 空间**（从 0.83 → 2.5），但需要无限发射、零延迟存储、完美预测

### 问题 4：分支预测准确率的影响

```
分支占比 ≈ 12.5%（每 8 条指令 1 条分支）
错误惩罚 = 15 cycles

预测准确率 → CPI 增量 → 性能影响
  100% (完美)   →  +0.00  →  baseline
   98% (顶尖)   →  +0.03  →  -3% 性能
   95% (优秀)   →  +0.09  →  -8% 性能
   90% (及格)   →  +0.19  →  -17% 性能
   80% (较差)   →  +0.38  →  -31% 性能

计算公式: CPI_penalty = branch_freq × (1 - accuracy) × miss_penalty
                = 0.125 × (1 - A) × 15
                = 1.875 × (1 - A)
```

**洞察**：对这段循环代码，循环分支 100% 可预测（TAGE 轻松拿满），所以预测器不是瓶颈。**但在不规则代码中，分支预测错误可能吃光 20-30% 的性能。**

### 问题 5：代码改写提升 IPC

观察原代码：`d[i] = a[i] * e[i]` 中 `a[i]` 是刚算出来的，又重新 load 一次（典型反模式）。

**优化后**：
```c
for (i = 0; i < 100; i++) {
    int a_val = b[i] + c[i];  // 保存在寄存器
    a[i] = a_val;
    d[i] = a_val * e[i];      // 直接用寄存器，无需 reload
}
```

**优化后效果**：
- 每次迭代 µop 数：8 → 7（少一次 lw）
- 关键路径：少 4 cycles（load 延迟）
- **新 IPC ≈ 0.95**（vs 0.83 优化前）
- **额外提升 ~14%**

**编译器会自动做这个优化吗？**
- 简单的 a[i] = b[i] + c[i]; d[i] = a[i] * e[i]; **不会**——因为 `a[i]` 是内存地址，编译器不能假设下次访问还能在 cache
- 改成显式寄存器变量 `a_val` 后，**会**自动优化
- 这是 **编译器 + 程序员协作优化** 的典型例子

### 进阶题

**Q6**：WSE 的 SLA PE 执行同样的循环，会是什么样？
- 没有乱序、没有分支预测、没有 Cache
- 但有 900K 个 PE 在并行
- **思路**：把数据布局到不同 PE 上，让每个 PE 负责一段 i 范围
- 例如 100 个 PE 各负责 1 个 i → 完全无依赖 → 单周期一条指令 → **等效 IPC = 1.0 per PE，900K 总 IPC**
- **但**：循环分支怎么解决？WSE 用数据流图，循环展开为静态 DAG

**Q7**：如果把这段代码改成 LLM 推理中的矩阵乘法 `C = A × B`，哪种架构更快？
- 假设矩阵 1024×1024，FP16
- CPU (4 发射 OoO): 受限于 FP16 吞吐和 Cache，~10 TFLOPS
- GPU (A100): Tensor Core 加速，~300 TFLOPS
- WSE-3: 900K PE × 1GHz × 2 (MAC) = **1.8 PFLOPS** (FP16)
- **差距**：WSE 比 CPU 快 180×，比 A100 快 6×

**Q8**：面积效率对比
- Intel Golden Cove 一核 ~6mm² @ 5GHz
- WSE-3 一 PE ~0.01mm² @ 1GHz（估算）
- 算力密度：Golden Cove ≈ 0.3 GFLOPS/mm²；WSE-3 PE ≈ 100 GFLOPS/mm²
- **WSE 单 PE 算力密度比 CPU 单核高 300×**
- 核心原因：CPU 80% 面积给了 OoO/Cache/分支预测这些"传统武器"，PE 100% 面积给了算力

```
│  ✅ 确定性延迟 (可建模 vs 难以预测)                         │
│  ✅ 算力密度 (100 GFLOPS/mm² vs 0.3)                      │
│  ✅ 编译器-硬件协同优化空间                                │
└────────────────────────────────────────────────────────┘
```

### 2. 你的研究方向对应的核心启示

| 你的方向 | 今天的关键启示 |
|---------|---------------|
| **超标量 CPU 核** | OoO + Cache + 分支预测的本质是"硬件帮软件擦屁股"。ILP 实际只有 2-4，再多硬件都换不来。 |
| **NPU 核** | 走 WSE 路线（领域专用 + 显式管理）比走"CPU + 加速器"路线在 AI 上更优。 |
| **NoC 拓扑** | 无 Cache Coherence 的 NoC 协议可以极度简化。2D Mesh + DOR 对 900K PE 仍然够用。 |
| **核内同步** | WSE 单时钟域天然同步是"反摩尔定律"的胜利——但代价是制造难度。 |
| **WSE 整体** | 简化 ≠ 弱化，而是**用软件复杂度换硬件复杂度**。 |
