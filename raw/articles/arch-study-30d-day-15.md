## 今日主题：虚拟内存 + TLB

### 🧭 为什么今天学这个？

前面 14 天我们一直在处理"程序视角的内存"——Cache、流水线、分支预测。但所有这些优化都基于一个隐含假设：**程序访问的地址都是物理地址**。

实际上，CPU 看到的地址是**虚拟地址**。从虚拟地址到物理地址的转换（**Address Translation**）是另一个独立的"性能战场"。如果这个转换本身很慢，再快的 Cache 也会被拖垮。

今天你将学到：
1. 虚拟内存解决了什么问题（不只是"扩展内存"那么简单）
2. **TLB** 如何成为新的性能瓶颈（甚至比 Cache Miss 更隐蔽）
3. 为什么现代 AI 芯片和 WSE **几乎完全抛弃了传统虚拟内存**——这是深思熟虑的工程决策，不是技术偷懒
4. 巨页 (Huge Pages) 为什么成为 AI 训练系统的"必修课"

核心问题：**WSE 为什么不需要 MMU/TLB？这个决策的代价和收益各是什么？**

## 🔑 核心概念（必须掌握）

### 1. 虚拟内存的四个核心作用

```
┌────────────────────────────────────────────────────┐
│  虚拟内存不只是"扩展物理内存"！它有 4 个独立作用       │
├────────────────────────────────────────────────────┤
│                                                    │
│  (1) 内存保护 (Protection)                          │
│      进程 A 不能访问进程 B 的内存                    │
│      → 硬件支持：每页有 R/W/X 权限位                │
│                                                    │
│  (2) 地址空间隔离 (Isolation)                       │
│      每个进程看到自己的"私有"地址空间                 │
│      → 简化程序员的内存模型（无需关心物理布局）      │
│                                                    │
│  (3) 内存扩展 (Demand Paging)                       │
│      程序可以"假装"自己有比物理内存更大的地址空间      │
│      → 只在访问时才把页从磁盘调入物理内存             │
│      → 必要时把不常用的页换出到磁盘                  │
│                                                    │
│  (4) 共享内存 (Sharing)                             │
│      多个进程可以映射同一物理页（代码段、共享库）      │
│      → fork() 的写时复制 (Copy-on-Write, COW)       │
└────────────────────────────────────────────────────┘
```

**对 WSE 的启示**：WSE 是单租户系统（一个 wafer 跑一个工作负载），所以 (1)(2)(4) 的需求大幅降低。但 (3) 的"按需分页"在 WSE 中并不需要——所有数据都是显式管理的。

### 2. 地址转换的完整流程

```
虚拟地址 (Virtual Address) 结构（以 RV32 Sv32 为例）：
┌──────────────────────────────────────────────┐
│  VPN[1] (10 bits)  │  VPN[0] (10 bits)  │ Offset (12 bits) │
│  1级页表索引        │  2级页表索引        │ 页内偏移          │
└──────────────────────────────────────────────┘

转换流程（2 级页表）：
  1. 从页表基址寄存器 (satp) 读出 1 级页表物理地址
  2. 用 VPN[1] 索引 1 级页表 → 读出 2 级页表物理地址（一次访存）
  3. 用 VPN[0] 索引 2 级页表 → 读出物理页框号 PPN（又一次访存）
  4. 拼出物理地址 = PPN + Offset

完成一次地址转换需要 **2 次额外访存**！
```

**性能灾难**：如果没有 TLB，每次内存访问都要先做 2 次页表查找，相当于把内存延迟 ×3！

### 3. TLB（Translation Lookaside Buffer）

```
TLB = 地址转换的 Cache

┌─────────────────────────────────────────────┐
│  TLB Entry 结构：                             │
│  ┌─────────────┬─────────────┬────────────┐ │
│  │  VPN (虚拟页号) │  PPN (物理页号) │ 权限位    │ │
│  └─────────────┴─────────────┴────────────┘ │
│                                              │
│  TLB 访问：                                    │
│  - 全相联或组相联查找（类似 Cache）            │
│  - 命中：直接得到 PPN（1 cycle）               │
│  - 未命中：需要走页表（硬件遍历或 page fault）  │
│                                              │
│  TLB 参数（典型值）：                          │
│  ┌────────────┬────────────┬──────────────┐  │
│  │ 名称        │ 大小       │ Hit Time      │  │
│  ├────────────┼────────────┼──────────────┤  │
│  │ L1 TLB     │ 32-128 项 │ ~1 cycle      │  │
│  │ L2 TLB     │ 256-2048项│ 5-10 cycles   │  │
│  │ 软 TLB     │ 操作系统维护│ 无固定延迟     │  │
│  └────────────┴────────────┴──────────────┘  │
└─────────────────────────────────────────────┘
```

**关键数据**：典型程序中，TLB 缺失率 = 1-2%。一次 TLB Miss 走页表要 30-100 cycles，Page Fault 走磁盘要数百万 cycles！

### 4. 修改后的 AMAT 公式（含 TLB）

```
AMAT = (TLB_Hit_Rate × (Cache_HitTime + TLB_Hit_Time)) 
     + (TLB_Miss_Rate × Page_Table_Walk_Time)
     + 后续 Cache 处理

简化版：
AMAT ≈ TLB_Hit_Time + TLB_Hit_Rate × Cache_AMAT
     + TLB_Miss_Rate × Page_Walk_Time
```

**关键洞察**：TLB 在访问路径的"前面"——如果 TLB Miss，Cache 都不用查！

### 5. 多级页表的必要性

```
问题：单级页表有多大？

RV32 32位虚拟地址 + 4KB 页 = 2^20 个页（1M 个页表项）
每个 PTE = 4 字节 → 单级页表 = **4MB**
→ 每个进程都要占 4MB 内存存页表！即使只用 100KB 也得全部分配

解决：多级页表（按需分配）

  2 级页表：
  - 1 级页表 = 4KB（固定）
  - 2 级页表：只有在 1 级页表项标记为"有效"时才分配
  - 总大小 ≤ 程序实际使用内存 + 4KB

  4 级页表（x86-64）：
  - PML4 → PDPT → PD → PT → 物理页
  - 每级 9 位索引 + 12 位 offset
  - 总虚拟地址 48 位（实际只用 48 位，剩余 16 位符号扩展）
```

### 6. 巨页 (Huge Pages) —— AI 训练系统的关键

```
传统页大小 = 4KB
  → 4GB 内存 = 1M 个页
  → TLB (128 项) 只能覆盖 512KB 内存
  → 任何 ≥ 512KB 的工作集都会产生 TLB 频繁失效

巨页 (Huge Page) = 2MB 或 1GB
  → 4GB 内存 = 2048 个 2MB 页 = 8 个 1GB 页
  → 128 项 TLB 可覆盖 256MB-128GB 内存
  → TLB 缺失率降低 100× 以上

Linux 配置：
  - 透明巨页 (THP)：内核自动合并小页
    → sysctl vm.transparent_hugepage=enabled
  - 显式巨页：程序通过 mmap() 申请
    → 适合已知大内存工作集（如 AI 训练）

AI 训练中：
  - 单个 LLM 训练：模型参数 + 优化器状态 + 梯度 = 几十 GB
  - 4KB 页 → TLB 完全无法覆盖
  - 2MB 巨页 → TLB 可覆盖大部分工作集
  - 1GB 巨页 → 极致性能（但预分配代价大）
```

**真实数据**：开启 THP 后，大模型训练性能通常提升 **5-15%**。

### 7. TLB Shootdown —— 多核时代的同步噩梦

```
问题：多核共享页表时，一个 CPU 改了页表项，其他 CPU 的 TLB 是过时的！

解决：TLB Shootdown
  1. 修改页表的 CPU 发出 IPI（核间中断）给所有其他 CPU
  2. 所有 CPU 刷新自己 TLB 中对应的项（或全部刷新）
  3. 等待所有 CPU 确认后，修改才生效

开销：
  - 一次 IPI 发送：~1-10 μs
  - 收到 CPU 刷新 TLB：~100 ns
  - 等待所有 CPU 响应：~10-100 μs（取决于核数）

  → 64 核机器上，一次 TLB Shootdown 可能耗 50-100 μs
  → 在系统调用密集型工作负载中，能占到 5-10% 的总时间
```

**研究热点**：Luke 你的"核内同步"方向，TLB Shootdown 是一个非常硬核的子问题——尤其在众核架构（WSE 900K PE 的规模）下，传统 IPI 方案完全不可行。

## 🧪 练习题（约 30-60 分钟）

### 基础题

**Q1**：某系统使用 32 位虚拟地址，4KB 页大小，2 级页表（每级 10 位索引）。问：
- (a) 单级页表需要多少项？占用多大内存？
- (b) 2 级页表在最坏情况下占用多少内存？
- (c) 一个程序实际使用 64KB 内存，2 级页表实际占多少？

> 答：
> (a) 2^32 / 4KB = 2^20 = 1M 项；1M × 4B = **4MB**（不管程序用多少）
> (b) 1 级页表 4KB（1 项 = 4B × 1024 项）+ 2 级页表（按需分配）
>     最坏 = 1 级表 + 1M 个 2 级表？不对，是 1 级表 + 1K 个 2 级表
>     = 4KB + 1K × 4KB = **4MB + 4KB**
>     实际最坏接近单级，因为每个 1 级表项都需要 1 个 2 级表
> (c) 64KB = 16 个页 → 16 个 2 级表项，分布在不同的 1 级表项中
>     1 级表 = 4KB（1 个）
>     2 级表 = ceil(16/1024) = 1 个 → 4KB
>     总计 = **8KB**（单级是 4MB 的 500 倍节省！）

**Q2**：某系统 TLB 参数如下：
- L1 TLB: 64 项，命中时间 1 cycle
- L2 TLB: 512 项，命中时间 8 cycles
- Page Walk 时间 = 30 cycles
- TLB 缺失分布：L1 Miss 率 5%，其中 L2 Hit 率 90%

计算一次内存访问的 TLB 平均开销。

> 答：
> 平均 TLB 查找时间 = 1 × 0.95 
>                   + (8 + 0.05 × 0.10 × 30) × 0.05
>     = 0.95 + (8 + 0.15) × 0.05
>     = 0.95 + 8.15 × 0.05
>     = 0.95 + 0.4075
>     = **1.36 cycles**
>
> 解读：L1 TLB 几乎全命中，平均开销主要来自 L1 Hit 本身。
> 如果 L1 TLB Miss 率上升到 20%：1 × 0.8 + 8.15 × 0.2 = 0.8 + 1.63 = 2.43 cycles
> → 性能下降 80%！所以 TLB 容量很关键。

**Q3**：一个 AI 训练任务占用 32GB 内存，访问模式是顺序流（每个字节访问一次后不再访问）。
- (a) 用 4KB 页需要多少 TLB 项才能覆盖工作集？
- (b) 用 2MB 巨页呢？
- (c) 真实 CPU 的 L1 TLB（64-128 项）能覆盖多少？

> 答：
> (a) 32GB / 4KB = 8M 个页 → 需要 8M 个 TLB 项（远超 L1 容量 64-128 项！）
> (b) 32GB / 2MB = 16K 个页 → 16K 个 TLB 项（仍然超出 L1 容量）
> (c) 128 项 TLB × 4KB 页 = 512KB 内存覆盖 / 32GB = **0.0016%**
>     128 项 TLB × 2MB 页 = 256MB 内存覆盖 / 32GB = **0.78%**
>     2 级 TLB（512 项）× 2MB = 1GB / 32GB = **3.1%**
>
> **结论**：AI 训练默认使用巨页（2MB 起步，1GB 最理想），且 L2 TLB 命中率才是性能关键。
> 这也是为什么 TPU 等专用 AI 芯片倾向于使用巨页或完全软件管理 TLB。

### 进阶题

**Q4**：多核系统中的 TLB Shootdown。
- 64 核系统，单次 Shootdown 处理时间（IPI 发出 + 所有 CPU 响应）= 30 μs
- 某多线程程序每 1 ms 进行一次 mmap()（触发 Shootdown）
- 程序本来单线程版本运行时间 100 ms

估算 Shootdown 对程序性能的影响。

> 答：
> 100 ms 期间发生 100 次 mmap → 100 次 Shootdown
> Shootdown 总开销 = 100 × 30 μs = 3 ms
> 占总时间 = 3 ms / 100 ms = **3%**
>
> 但实际开销更大：mmap() 期间持有锁，其他线程被阻塞
> 真实场景下，开销可达 **10-30%**
> 这就是为什么 AI 训练系统倾向于"启动时一次预分配，运行中不分配"

### 思考题（与 WSE 研究关联）

**Q5**：Cerebras WSE-3 没有 MMU，没有 TLB，没有传统虚拟内存。每个 PE 直接寻址自己的 48KB SRAM + 通过 NoC 寻址远端 PE SRAM。
- (a) 这种设计"放弃"了虚拟内存的哪些好处？
- (b) 这种设计"获得"了哪些好处？
- (c) 一个不规则的、需要动态内存分配的工作负载，在 WSE 上会遇到什么问题？
- (d) 你的 NPU 研究方向可以从中学到什么？

> 答（思路）：
> **(a) 放弃的好处：**
> 1. 进程隔离（WSE 上只有一个"程序"）
> 2. 需求分页（按需从磁盘调入）—— WSE 没有磁盘，所有数据常驻 SRAM
> 3. 写时复制（COW）—— 没有 fork() 这种系统调用
> 4. 动态内存分配（malloc/free）—— 需要程序员显式管理
>
> **(b) 获得的好处：**
> 1. **确定性**：地址转换开销 = 0，无 Page Fault
> 2. **性能可预测**：所有访存延迟可精确计算
> 3. **简化硬件**：省下 MMU/TLB 面积（约 1-2% 芯片面积）和功耗
> 4. **简化编程模型（部分）**：程序员直接看到物理地址
>
> **(c) 不规则工作负载的问题：**
> 1. 动态数据结构（链表、哈希表）—— 难以静态映射到固定 PE
> 2. 稀疏访存 —— 局部性差，NoC 拥塞
> 3. 内存溢出 —— 必须在编译时知道最大数据量
> 4. 指针追逐 —— 远端 PE 访问延迟高，乱序 NoC 路由复杂
>
> **(d) 对 NPU 设计的启发：**
> 1. **领域专用化 (DSA) 的极致**：在规则的 AI 工作负载上，软件管理 > 硬件猜测
> 2. **可预测性 > 平均性能**：AI 推理对延迟尾部敏感
> 3. **数据流编程模型** (CSL/SpaDA) 是 WSE 性能的关键 —— 程序员+编译器把"该用哪个地址"提前算好
> 4. 你的 NPU 设计方向可以参考：用显式数据流 + 编译器优化，取代复杂的硬件管理单元（TLB、Cache Controller、Out-of-Order Engine）
> 5. 代价是失去了通用性 —— WSE 只能跑 AI 工作负载，跑不动 Word

## 🔗 与 WSE / NoC / NPU 研究的关联

### 虚拟内存视角：WSE 的"激进简化"决策

```
┌────────────────────────────────────────────────────────┐
│  传统处理器中的"地址转换 + Cache 层次"双层结构：          │
│                                                        │
│  虚拟地址 ─→ TLB ─→ 物理地址 ─→ Cache ─→ 物理数据        │
│             ↑                ↑                          │
│             │                │                          │
│         缺失→走页表        缺失→走下层                   │
│                                                        │
│  两层独立的"猜测机制"互相叠加，复杂度爆炸                │
└────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────┐
│  WSE 的"激进简化"：                                    │
│                                                        │
│  程序员/编译器 ─→ 物理地址 ─→ SRAM 数据                 │
│                  ↑            ↑                        │
│                  │            │                        │
│              显式给出      必然命中                     │
│                                                        │
│  完全消除了"地址转换的猜测"和"数据的猜测"               │
└────────────────────────────────────────────────────────┘
```

### WSE 的简化代价：数据流编程模型

WSE 用 CSL (Cerebras Software Language) / SpaDA 编程，本质上是把"程序员手工完成的工作"显式化：

```
传统 CPU 上的"隐式工作"：
  - malloc/free → 硬件管理的虚拟内存 + TLB
  - 顺序代码 → 硬件乱序执行 + 分支预测
  - 任意数据访问 → Cache + TLB 自动定位

WSE 上的"显式工作"：
  - 内存分配 → 编译时静态确定每个 PE 持有什么数据
  - 控制流 → 编译时生成数据流图
  - 数据访问 → 编译时插入显式的 NoC 消息

这是 "Software-Managed Everything" (SME) 哲学
  → 程序员 + 编译器 = 优化器
  → 硬件 = 简单执行单元
```

### 对 NoC 的影响

WSE 的 NoC 不需要支持：
- **Cache Coherence Traffic**（无共享地址空间）
- **TLB Shootdown IPI**（无共享页表）
- **Memory Ordering**（无多核共享变量）

WSE 的 NoC 只需要支持：
- **确定性数据流**（编译时已知路径）
- **静态/动态 Reconfigurable Fabric**（CSL 描述的连接）
- **稀疏突发通信**（权重分发、梯度聚合）

→ NoC 协议大幅简化，硬件实现更高效，面积开销更小

### 对 NPU 设计的启示

```
从 WSE 得到的 NPU 设计原则：

1. 避免硬件"猜测"机制
   - 不做 TLB 猜测 → 不做复杂 Cache
   - 不做分支预测 → 编译时数据流图
   - 不做 Cache Coherence → 软件显式同步

2. 优化"程序员视角的可预测性"
   - 固定延迟（不要"平均延迟"）
   - 可建模（编译期能算出的执行时间）

3. 接受"通用性损失"
   - 你的 NPU 只能跑特定工作负载

4. 把复杂性移到软件栈
   - 编译器是核心
   - 编程语言设计（CSL/MHAL）至关重要
```

*Day 15 / 30. 今天我们看到的 TLB 其实是体系结构中"被低估的瓶颈"——很多程序员甚至不知道它的存在。但对 AI 工作负载而言，TLB 缺失的代价可能比 L3 Cache Miss 还要高。WSE 的"激进简化"哲学告诉我们一个深刻道理：**复杂的硬件机制（如 MMU/TLB）不是为了"通用性"而存在的，而是为了掩盖"软件不知道数据在哪"这一事实**。当你愿意把"软件知道"这件事推向极致，硬件就可以变得极其简单。这是体系结构设计中最深刻的取舍之一，也是 DSA (Domain-Specific Architecture) 时代的主旋律。*
